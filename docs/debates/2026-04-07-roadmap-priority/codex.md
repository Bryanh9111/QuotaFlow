1. **Premature:** `1, 2, 5, 6, 7, 8, 9, 11`. One real task is not a usage pattern. It is an anecdote. There is no evidence QuotaFlow needs backend abstraction, a richer storage model, a dashboard, dependency orchestration, multi-client architecture, sub-agents, or GC policy. The current product is still proving whether it can repeatedly make good dispatch decisions for one operator on one machine. Building scale features now is how you bury the signal under architecture.

2. **Drop entirely:** `5 Web dashboard`, `7 Task dependencies`, `8 Client-server`, `9 Sub-agent`, `10 Boundary tests`, and I would argue `6 Per-project budget` too. Dashboard is UI vanity for a CLI daemon. Dependencies turn a simple queue into a workflow engine. Client-server destroys the main virtue of the current design: local, low-ops, low-blast-radius. Sub-agents are actively dangerous when your only real datapoint is a 908k-token planning run; that is how you multiply burn rate and coordination noise. “Boundary tests” should not be a roadmap item at all because the codebase already has broad scheduler/quota edge coverage in [tests/scheduler.test.ts](/path/to/workspace/QuotaFlow/tests/scheduler.test.ts#L201) and related tests. That is hygiene, not product strategy.

3. **Top 3 for this week:** `3 AGENTS.md`, `4 Enhanced digest`, `2 History DB` only if it means “minimal instrumentation,” not “new subsystem.”
   `3 AGENTS.md` because the immediate problem smells like prompt/task discipline, not missing software. You need hard constraints: mandatory decomposition, explicit stop conditions, capped plan depth, smaller deliverables.
   `4 Enhanced digest` because current reporting is too weak. Daily digest only shows completed/failed/utilization in [src/notify.ts](/path/to/workspace/QuotaFlow/src/notify.ts#L76), and CLI status only shows weekly tokens and task count in [src/cli.ts](/path/to/workspace/QuotaFlow/src/cli.ts#L132). It does not surface “ProjectBeta consumed most of the week,” outliers, estimate error, or project concentration.
   `2 History DB` only as an extension of the existing SQLite log, not a separate architecture. You need real run history by project/size/outcome so future prioritization is based on evidence.

4. **The 908k-token ProjectBeta run is a deeper problem.** It already falsified the sizing model. QuotaFlow still assumes `large = 60k` in [src/types.ts](/path/to/workspace/QuotaFlow/src/types.ts#L85), and queue admission still relies on those estimates in [src/queue.ts](/path/to/workspace/QuotaFlow/src/queue.ts#L112). Your only real production datapoint was roughly 15x larger than “large.” That is not a small miss. That means the system’s control loop is built on fake units. It gets worse: adaptive estimation exists, but the scheduler records usage without task size, so it cannot actually learn correctly from completed runs in [src/quota.ts](/path/to/workspace/QuotaFlow/src/quota.ts#L105). The issue is not “we need more features.” The issue is “we do not yet control task scope.”

5. **Strongest argument against per-project budget:** it substitutes fairness theater for value. Budgets create false precision in a system that still cannot size work reliably. They also invite gaming: split ProjectBeta into fake projects, relabel tasks, or hoard quota politically. If ProjectBeta is the highest-value work, it should be allowed to consume most of the week. The fix is stricter task scoping and better kill-switches, not arbitrary envelopes.
